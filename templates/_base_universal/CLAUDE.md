## ЖУРНАЛ ПРОЕКТА И КОММИТЫ — ГЛАВНОЕ ПРАВИЛО

Этот шаблон ведёт **журнал**, чтобы проект можно было передать другому
исполнителю — другой нейронке или человеку — без потери контекста. Любой,
кто откроет проект, должен понять **что делали, где сейчас и куда идём**,
не читая весь код.

**Память проекта — пять файлов. Точка входа: [docs/handoff.md](docs/handoff.md).**

| Файл | Роль | Как меняется |
|------|------|--------------|
| `docs/handoff.md` | С чего начать новому исполнителю | при передаче |
| `docs/project-brief.md` | Что за проект и зачем | редко |
| `docs/state.md` | Где мы **сейчас** + следующие шаги | постоянно (перезапись) |
| `docs/changelog.md` | Что уже **сделано**, по датам | дописывается вниз |
| `docs/decisions.md` | **Почему** так, а не иначе | дописывается вниз |

**Железное правило — после каждого осмысленного шага:**

1. Обнови `docs/state.md` — где сейчас и что дальше.
2. Допиши `docs/changelog.md` — одна запись про шаг.
3. Был неочевидный выбор? — запись в `docs/decisions.md` (D-NNN).
4. Снимок в git: `bash scripts/snapshot.sh "<что сделали>"`.

Проще всего — слэш-команды (делают всё это сами):
`/log` — записать шаг и закоммитить · `/decision` — зафиксировать решение ·
`/handoff` — собрать снимок передачи.

«Осмысленный шаг» = добавили фичу, починили баг, задеплоили, приняли
решение, закончили рабочую сессию. Не нужно коммитить каждую строчку —
коммить законченные кусочки.

**Почему так:** история проекта = git-коммиты + `docs/`. `state.md`
отвечает «где мы», `changelog.md` — «что было», `decisions.md` — «почему».
Этого достаточно, чтобы кто угодно подхватил проект с того места, где его оставили.

### Вопрос 3 — Где будет жить приложение

*"Где мы разместим приложение?"*

**Варианты:**

- **Vibecode** — хостинг от Битрикс24. Деплой одной командой, всё уже настроено.
  **→ Рекомендую для большинства проектов.**
- **Свой сервер** — полный контроль, но требует ручной настройки.
  Выбирай если: нужны особые требования к безопасности или уже есть инфраструктура.
- **Ещё не знаю** — запишем, разберёмся позже.

---

### Вопрос 4 — Как подключаемся к Битрикс24

*"Как приложение будет получать данные из Битрикс24?"*

**Варианты:**

- **API-ключ (vibe_api_...)** — один ключ на портал, все видят одни данные.
  Просто: создал ключ, вставил в настройки, работает.
  **→ Рекомендую для дашбордов и инструментов администратора.**
- **OAuth-приложение (vibe_app_...)** — каждый сотрудник входит через свой аккаунт Б24.
  Каждый видит только свои данные. Сложнее в настройке.
  Выбирай если: важно разграничение прав между сотрудниками.
- **Без Битрикс24** — приложение не работает с данными Б24 напрямую.

---

### Вопрос 5 — Где открывается приложение

*"Где пользователь будет открывать приложение?"*

**Варианты:**

- **Внутри Битрикс24** — вкладка в меню, виджет в карточке CRM, кнопка в сделке.
  Выглядит как часть Б24. **→ Рекомендую для инструментов сотрудников.**
- **Отдельная страница** — открывается в браузере, не зависит от Б24.
  Выбирай если: это отдельный сервис или клиент не использует Б24 интерфейс.
- **Оба варианта** — и внутри Б24, и как отдельная страница.

---

### Вопрос 6 — Нужен ли серверная часть (бэкенд)

*"Приложению нужна серверная часть?"*

**Варианты:**

- **Нет, только фронт** (HTML + JS) — подходит для простых дашбордов и виджетов.
  Данные берутся прямо из Битрикс24. **→ Рекомендую если нет сложной логики.**
- **Да, Node.js** — нужен если: авторизация пользователей, хранение данных,
  сложная обработка, интеграция с другими сервисами.
- **Не знаю** — опиши задачу, помогу определиться.

---

### Вопрос 7 — Дизайн

*"Как должно выглядеть приложение?"*

**Варианты:**

- **Стиль Битрикс24** — выглядит как часть платформы, знакомо сотрудникам.
  **→ Рекомендую для виджетов и инструментов внутри Б24.**
- **Нейтральный современный** — чистый, профессиональный вид. Подходит
  для отдельных приложений и сервисов.
- **Корпоративный стиль клиента** — используем цвета и шрифты клиента.
  Потребуется описание стиля или брендбук.

---

### Вопрос 8 — Авторизация пользователей

*"Нужно ли пользователям входить в приложение?"*

**Варианты:**

- **Не нужна** — приложение открыто для всех у кого есть ссылка.
  **→ Рекомендую если доступ уже ограничен через Битрикс24** (приложение видят только нужные сотрудники).
- **PIN-код** — простая защита: сотрудник вводит цифровой код.
  Выбирай если: нет Б24 и нужна минимальная защита (как в проекте "Балтийская группа").
- **Через Битрикс24** — сотрудник входит своим аккаунтом Б24 (OAuth).
  Выбирай если: нужно знать кто именно работает с приложением.
- **Своя авторизация** — логин/пароль или другой способ. Опиши задачу, разберёмся.

## КЛЮЧИ И БЕЗОПАСНОСТЬ

**Правило №1: Ключи никогда не попадают в код и в git.**

Все ключи хранятся в файле `.env`. Этот файл есть в `.gitignore`.
В git попадает только `.env.example` — шаблон без реальных значений.

**Типы ключей VibeCode:**

| Тип | Префикс | Когда использовать |
|-----|---------|-------------------|
| API-ключ | `vibe_api_...` | Личный дашборд, скрипты, один портал |
| OAuth-приложение | `vibe_app_...` | Команда, у каждого свои права в Б24 |
| Менеджмент | `vibe_live_...` | Только для администрирования, не для данных |

**Переменные `.env` (стандартный набор):**

```
# VibeCode
VIBE_API_KEY=vibe_api_...         # API-ключ портала
VIBE_BASE_URL=https://vibecode.bitrix24.tech/v1

# Сервер (заполняется после первого деплоя)
SERVER_ID=                         # ID сервера на Vibecode
PORT=3000
NODE_ENV=production
```

**Где получить ключ:** https://vibecode.bitrix24.tech → Ключи API → Создать

**Правило №2: При подозрении на утечку ключа — сразу отозвать** в личном кабинете Vibecode и создать новый. Обновить `.env` на сервере.

## MCP-СЕРВЕРЫ

MCP — это инструменты, которые позволяют Клоду напрямую обращаться к API и документации прямо из редактора. Подключаются через `.claude/settings.local.json`.

**Два обязательных MCP для всех проектов:**

1. **vibecode** (`mcp-vibe-api`) — прямой доступ к VibeCode API: сущности, боты, чаты, телефония
2. **bitrix24-docs** (`mcp-bitrix24-docs`) — поиск по официальной документации Битрикс24 REST API

**Установка (один раз на машину):**
```bash
npm install -g mcp-vibe-api mcp-bitrix24-docs
```

Локальная версия и продакшн на Vibecode **всегда должны быть идентичны**.

## ПАТТЕРНЫ РАЗРАБОТКИ

Эти правила выработаны из реальных проектов. Следовать им по умолчанию.

### API-клиент
- VibeCode может возвращать данные в двух форматах: `data.result` и `data.data` — всегда проверяй оба
- Пагинация: запрашивай по 50 записей, повторяй пока результат < limit
- Батчи: до 25 параллельных запросов (больше — риск попасть в rate limit: 60 запросов/мин)

### Кеширование
- Тяжёлые отчёты: храни в памяти (Map) + дублируй на диск (JSON)
- На сервере Vibecode: кеш в `/opt/data/` — переживает деплой
- Локально: папка `data/` (в .gitignore)

### Деплой на Vibecode
- `cleanDeploy=true` — чистая установка каждый раз (папка `/opt/app/` стирается)
- Данные храни в `/opt/data/`, не в `/opt/app/`
- Runtime: `node20`

### Фронтенд
- Vanilla JS + CSS — никаких фреймворков без явной необходимости
- CSS custom properties (`--var`) для цветов и отступов — легко менять тему
- Chart.js через CDN — не тащить в сборку

### Битрикс24 iframe
- Б24 загружает приложение и отправляет POST на `/` с данными о размещении
- Сервер должен отвечать на POST `/` так же как на GET `/` — отдавать `index.html`
