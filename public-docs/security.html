Vibe Portal · security model

Изоляция учеников и отделение vibe от dev

Как мы заперли учебные контейнеры на одном сервере с продакшеном dev-портала — для среднего разработчика, без воды.

Часть 1. Защита сервера от учеников

Ученик внутри своего контейнера — это, считай, человек с root'ом в Debian 12 и интернетом. Задача: максимум, что он может наружу — пойти в npm/github и постучаться в наш anthropic-shim. Всё остальное на машине для него не существует.

Защита строится в четыре слоя: container caps → docker network → iptables → shim.

1.Контейнерные капы (последняя линия обороны)

Запуск под пользователем student (uid 1000), без sudo:

# docker run
--user 1000:1000
--cap-drop=ALL
--no-new-privileges
--memory=1.5g --cpus=1.0

Это страховка на случай kernel-LPE или namespace-бага: без капов и с no-new-privileges эскалация заметно сложнее.

Bind-mount'ы выданы точечно:

  • /data/vibe-students/<user> → /home/student/workspace (только своя папка, rw)
  • /opt/vibe-portal/templates → /home/student/templates (ro)

Чужих workspace'ов он не видит просто потому, что их нет в mount-table. Хостовая ФС вообще не торчит.

2.Своя docker-сеть vibe-net

Все контейнеры учеников живут в отдельном bridge br-vibe (172.30.0.0/24). Inter-container communication выключен — даже если двое учеников онлайн одновременно, пакет от Васи к Пете дропается на самом мосту.

3.iptables — главный замок

Файл scripts/setup-iptables.sh собирает две цепочки и подвешивает их раньше дефолтных docker-правил. Важно: VIBE-FILTER цепляется в DOCKER-USER, которая срабатывает до автодженерённых docker-правил — иначе ничего бы не работало.

VIBE-FILTER — контейнер → внешний мир:

1. ESTABLISHED/RELATED            ACCEPT   ← return-трафик
2. dst 172.30.0.1:8190             ACCEPT   ← shim, единственная разрешённая хостовая служба
3. dst 172.30.0.1 (любой порт)     DROP     ← всё остальное на gateway
4. dst 10/8, 172.16/12, 192.168/16 DROP     ← другие docker-bridges, RFC1918
5. dst 169.254/16, 127/8           DROP     ← link-local, loopback, cloud metadata
6. dst 80.87.104.193               DROP     ← публичный IP сервера (NAT-loopback)
7. остальное                       ACCEPT   ← интернет (npm, github, dns)

VIBE-INPUT — контейнер → IP хоста:

1. ESTABLISHED/RELATED            ACCEPT
2. dst 172.30.0.1:8190             ACCEPT
3. всё остальное                  DROP     ← sshd, nginx, postgres хоста — для ученика их нет

Что это вместе блокирует:

  • другие docker-bridges (dev-portal, postgres, что угодно) — RFC1918 целиком в DROP'е;
  • других vibe-учеников — их IP тоже в 172.30/24, попадают в drop по 172.16/12;
  • 127.0.0.1 хоста — vibe-panel:3020, dev-сервисы недоступны;
  • публичный IP сервера — главное: иначе ученик бы постучался в 80.87.104.193:443 и попал на наш же nginx (NAT-loopback), оттуда на dev-портал. Закрыли явным DROP по HOST_PUBLIC_IP;
  • 169.254/16 — на случай cloud metadata endpoints.

Применяется при загрузке через vibe-iptables.service (oneshot). Скрипт идемпотентный — можно дёргать руками, ничего не сломается.

4.Anthropic-shim — единственная «дырка» наружу

shim/server.js на хосте слушает :8190, принимает запросы только с 172.30.0.0/24 и 127/8 (whitelist в коде, поверх iptables — defence in depth). Внутри:

  • срывает Authorization от ученика;
  • подставляет настоящий Bearer из /data/config/auth/claude-vibe.credentials.json (chmod 600, не в git);
  • форвардит в api.anthropic.com через внешний HTTP-прокси.
Ключевая идея
Ученик никогда не видит наш OAuth-токен Claude. Он живёт только на хосте, в файле с chmod 600, и контейнер до него не дотягивается ни по сети, ни по ФС.

Карта разрешённого трафика

┌──────────────────────────┐ │ vibe-<user> container │ 172.30.0.X │ uid 1000, no caps │ └────────────┬─────────────┘ │ ├─→ 172.30.0.1:8190 shim → api.anthropic.com ├─→ internet (53, 80, 443) npm, github, dns │ ├─✗ 10/8, 172.16/12, 192/16 другие docker-сети, RFC1918 ├─✗ 127.0.0.1 vibe-panel, dev, postgres ├─✗ 80.87.104.193 nginx публичный (NAT-loopback) ├─✗ 169.254/16 cloud metadata └─✗ vibe-net peers ICC off + drop по 172.16/12

Часть 2. Изоляция vibe от dev

Vibe и dev-portal крутятся на одном сервере (80.87.104.193), но это два независимых проекта — общего у них только git-репо для бэкапа и сам факт хостинга.

По коду

  • Раньше vibe жил подкаталогом в /opt/dev-portal/vibe/. 2026-05-26 вынесли в /opt/vibe-portal/ целиком.
  • Шаблоны переехали из /opt/dev-portal/templates/vibe/ в /opt/vibe-portal/templates/.
  • В vibe нет импортов из dev. Свой panel/server.js, свой lib/, свои public-ассеты. Визуально похоже (тёмная тема, IBM Plex Mono), но это копия стилей, не shared-модуль.

По auth

Отдельная стопка:

  • /data/config/auth/.htpasswd-vibe — отдельный htpasswd;
  • /data/config/auth/users-vibe.json — отдельный список пользователей с ролями;
  • /data/config/sessions-vibe/ — отдельный session-file-store;
  • свой SESSION_SECRET в /data/config/env/vibe-panel.env.

Залогиниться в dev-портал учёткой vibe-ученика физически невозможно — это разные базы и разные процессы вообще не делятся сессиями.

По сети — это ключ

Тут как раз работает та же VIBE-FILTER-цепочка. Контейнеры dev'а сидят в других docker-bridges (10.x / 172.17.x / 172.18.x — стандартные docker-диапазоны). Все они попадают под правила:

-A VIBE-FILTER -d 10.0.0.0/8    -j DROP
-A VIBE-FILTER -d 172.16.0.0/12 -j DROP

Пакет от vibe-ученика в сторону любого dev-контейнера дропается на FORWARD-стадии. Плюс ученик не может постучаться в 127.0.0.1 хоста — а значит не достанет dev-panel, не достанет postgres, не достанет ничего, что слушает loopback. И не может обойти это через NAT-loopback по публичному IP — мы отдельно дропнули 80.87.104.193.

По бэкапу — единственное общее

/opt/dev-portal/scripts/backup-all.sh rsync'ит и /opt/dev-portal/, и /opt/vibe-portal/ в /srv/server-backup/ и пушит в один gitflic-репо (vibe лежит подпапкой vibe-portal/). Это операционное удобство, на runtime-изоляцию никак не влияет.

TL;DR
Ученик заперт в docker-контейнере без капов, его сеть пропущена через явный iptables-whitelist, где открыто ровно две вещи — shim:8190 и публичный интернет (минус наш собственный IP). Всё остальное — другие ученики, dev-portal, хостовые сервисы, loopback, metadata-endpoints — задропано на уровне ядра. Vibe и dev делят железо и git-репо для бэкапа, но не делят ни код, ни auth, ни сеть, ни процессы.
