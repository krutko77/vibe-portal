## D-001 — chat-history как проектный скилл, не глобальный (2026-07-21)

**Контекст:** нужен был скилл для экспорта истории сессий Claude Code в читаемый Markdown.
**Варианты:** глобальный скилл (`~/.claude/skills/`, доступен в любом проекте) или проектный (`.claude/skills/`, только в vibe-portal).
**Решение:** проектный, вывод — в `.claude/chat-history/` (добавлено в `.gitignore`).
**Почему:** пользователь явно выбрал ограничить область vibe-portal; личный рабочий лог не должен уходить в git/бэкап-снапшот кодовой базы.
**Последствия:** в других проектах скилл придётся ставить заново; экспортированные `.md` не коммитятся и не бэкапятся общим `backup-all.sh` (в текущей конфигурации).

## D-002 — установка команд /end, /decision, /handoff, /log из репозитория ученика курса (2026-07-21)

**Контекст:** ученик курса (`krutko77`, есть в `users-vibe.json`) поделился ссылкой на свой репозиторий `github.com/krutko77/scills-claude` с набором Claude-команд для журналирования сессий.
**Варианты:** установить не глядя; отказаться, т.к. источник — ученик, а команды исполняются в хостовой admin-сессии с полными правами; прочитать содержимое каждого файла перед установкой и решить по факту.
**Решение:** каждый файл (`end.md`, `decision.md`, `handoff.md`, `log.md`) прочитан целиком перед установкой. Подозрений не подтвердилось — только чтение/запись `docs/*` и `git commit` через `scripts/snapshot.sh`, ни сетевых вызовов, ни обращения к секретам. Установлены как команды `.claude/commands/*.md`, под них создана инфраструктура `docs/state.md`, `docs/changelog.md`, `docs/last-session.md`, `docs/handoff.md`, `docs/decisions.md`, `scripts/snapshot.sh`.
**Почему:** содержимое безопасно и полезно (дисциплина хендоффа между сессиями); риск не в конкретных файлах, а в бесконтрольной установке кода с любого внешнего источника — этот риск закрыт построчным ревью перед установкой, а не отказом.
**Последствия:** `scripts/snapshot.sh` делает `git add -A` — перед первым запуском любой из команд (`/end`, `/log`, `/handoff`, `/decision`) стоит проверять `git status`, чтобы случайно не закоммитить что-то лишнее из untracked.

## D-003 — фикс изоляции vibe-net: динамическое имя моста вместо переименования интерфейса (2026-07-22)

**Контекст:** `scripts/setup-iptables.sh` хардкодил `BR="br-vibe"`, а реальный bridge-интерфейс сети `vibe-net` называется `br-92be0fc90d9e` (docker сам генерит имя как `br-<первые 12 hex ID сети>`, кастомное имя через `com.docker.network.bridge.name` никогда не было выставлено). Итог: правила `VIBE-FILTER`/`VIBE-INPUT` не матчали ни один пакет — изоляция между контейнерами учеников и блок доступа к хостовым сервисам не работали (0 pkts на всех правилах).
**Варианты:** (1) переименовать живой интерфейс `ip link set br-92be0fc90d9e name br-vibe`, как было предварительно записано в CLAUDE.md; (2) поправить `setup-iptables.sh`, чтобы имя моста вычислялось из `docker network inspect vibe-net` при каждом запуске.
**Решение:** вариант (2).
**Почему:** имя интерфейса живёт только в ядре и не персистентно — docker создаёт bridge заново с дефолтным именем `br-<ID>` при пересоздании сети или после ребута хоста (интерфейсы не переживают перезагрузку). Ручной `ip link set` дал бы правильный результат прямо сейчас, но тихо откатился бы при следующей перезагрузке сервера, а systemd-юнит `vibe-iptables.service` как раз и гоняется `After=docker.service` при каждой загрузке — баг вернулся бы без явных симптомов. Динамическое определение имени устойчиво к ребуту и пересозданию сети, не трогает живую сеть контейнеров вообще (только правила iptables, что и так штатно идемпотентно).
**Последствия:** после правки пришлось вручную снять старые hook-правила в `DOCKER-USER`/`INPUT` (ссылались на несуществующий `br-vibe`, из-за чего `iptables -D` по новому имени их не находил и `vibe-iptables.service` падал с "CHAIN_DEL failed: Device or resource busy") — разовая ручная чистка, дальше юнит идемпотентен сам по себе. Проверено практически на `vibe-krutko77`: shim (172.30.0.1:8190) доступен, хостовый порт :3020 и публичный IP хоста — задропаны, внешний интернет — доступен; счётчики пакетов в `VIBE-FILTER`/`VIBE-INPUT` подтверждают срабатывание нужных правил.

## D-004 — deploy-service вместо root/sudo контейнерам; заодно фикс той же болезни для HOST_PUBLIC_IP (2026-07-24)

**Контекст:** агент (claude-cli) внутри проекта `es-trans_repairs` (`/home/my_workspace`, реальный клиентский деплой на `repairs.es-trans.ru`, а не курсовой сэндбокс) уткнулся в отсутствие root на сервере `201.51.4.183` и попросил пользователя выдать пароль root или `NOPASSWD:ALL` в sudoers. В процессе разбора выяснилось: (1) `201.51.4.183` — это тот же самый хост, что держит весь vibe-portal/dev-portal, не отдельная клиентская машина; (2) на нём уже полностью развёрнута и живая инфраструктура (nginx+certbot+pm2) для 5 es-trans-сайтов; (3) `scripts/setup-iptables.sh` дропал публичный IP хоста по хардкоду `80.87.104.183`, а реальный (DHCP) адрес хоста — как раз `201.51.4.183` — то есть анти-NAT-loopback защита, которую чинили в D-003 два дня назад, снова не работала (0 совпадений), и это, вероятно, и есть канал, которым агент вообще дотянулся до хоста.
**Варианты:** (А) пароль root в чат; (Б) `student ALL=(ALL) NOPASSWD:ALL` в sudoers на хосте; (В) `setcap cap_net_bind_service` на node — не годится в одиночку, т.к. контейнеры физически не могут достучаться до хоста (iptables), значит sudoers/setcap бесполезны без открытия сети; (Г) сделать контейнер `--privileged`/`--network host` — отвергнуто пользователем как разрушающее вообще всю изоляцию контейнера; (Д) держать курсовую multi-tenant архитектуру и root/sudo не давать вообще, а поднять узкий сервис на gateway-IP `172.30.0.1:8191` (по образцу anthropic-shim), доступный только из `vibe-net` через отдельное iptables-правило, который сам выполняет rsync+nginx+certbot+pm2 от root по запросу агента.
**Решение:** вариант (Д) — `deploy-service` (`systemd/vibe-deploy.service`, код в `deploy-service/`). Владельца определяет по source-IP контейнера (как `shim/transcript.js`), так что агент не может задеплоить чужой проект. Домен ограничен `*.es-trans.ru`, `entry`/`install_cmd` из `.vibe-deploy.json` валидируются (без произвольного shell). Реестр `/etc/vibe-deploy/registry.json` заведён вручную только для 3 однозначно матчащихся легаси-проектов (repairs/orders-and-transportation/tests-results); остальные легаси-сайты (standard, test-2, a1track-PHP) не размапплены — риск случайно перезаписать чужой домен из-за несовпадения имени папки и pm2-процесса. Заодно поправлен `HOST_PUBLIC_IP` в `setup-iptables.sh` — вместо хардкода вычисляется список всех global-scope IPv4 хоста при каждом запуске (та же логика, что уже применили к `BR` в D-003).
**Почему:** узкий сервис даёт агенту ровно то, что нужно (задеплоить свой же проект), не открывая ни root, ни сеть хоста целиком; blast radius одного скомпрометированного/ошибшегося агента — максимум его собственные `*.es-trans.ru`-сайты, а не весь хост. Хардкод IP — системная ошибка того же класса, что и `BR` в D-003 (значение, вычисленное один раз и не переживающее смену состояния хоста); исправлено тем же способом — вычислением при каждом запуске вместо жёсткого значения.
**Последствия:** новый открытый порт на gateway (172.30.0.1:8191, ACCEPT только из vibe-net) — расширяет периметр `vibe-net → host` на одну узкую операцию, задокументировано в CLAUDE.md. Для проектов `es-trans-standard`/`test-2`/`a1track` авто-деплой пока недоступен — при необходимости мапить вручную в registry.json (проверить реальное соответствие домен↔pm2↔каталог перед добавлением, не гадать по имени). Сквозной прогон проверен на живом хосте: health, unknown-container (403), path-traversal (400), полный happy-path на одноразовом тестовом проекте (nginx+certbot-graceful-fail+pm2), артефакты теста убраны, живые pm2/nginx не тронуты.

## D-005 — регистрация es-trans-standard + a1track; тип "php" в реестре (2026-07-24)

**Контекст:** пользователь попросил зарегистрировать в deploy-service (D-004) оставшиеся два легаси-проекта — `es-trans-standard` и `a1track`. Проверка по именам (как предупреждал D-004) оказалась ловушкой: домены `test-1`/`test-2.es-trans.ru` НЕ совпадают по номеру с ожидаемым по названию pm2-процессом — сверка по факту (`pm2 jlist` → pid, `ss -ltnp` → какой pid слушает какой порт) показала, что `test-1` реально проксируется на процесс `es-trans-test` (порт 3000), а `test-2` — на `es-trans-standard` (порт 3001). Наивный `diff` между `src/server.js` обоих деплоев тоже не помог бы отличить их — код в обоих оказался побайтово идентичен. Отдельно `a1track` — не Node/pm2, а PHP (php-fpm) с исходником в подпапке `www/` проекта (не в корне), плюс прод-файлы `env.php` (реальные `B24_CLIENT_ID`/`SECRET` Bitrix24) и `data/` (рантайм-стор токенов/сессий), которых в воркспейс-копии либо нет, либо там dev-заглушка — существующий код деплоя (`rsync --delete` без исключений + всегда `npm install`+`pm2`) их бы или снёс, или попытался бы поставить npm-зависимости в PHP-проект.
**Варианты:** (1) смэппить `a1track` под существующий `type:"node"`-путь, добавив костыль в самом registry.json (не годится — код всё равно жёстко предполагает pm2/port); (2) расширить `handleDeploy` вторым типом `"php"` (rsync + chown, без pm2/install/nginx-provision) с полями `src_subdir`/`exclude`; (3) сделать отдельный отдельный http-endpoint под PHP — избыточно для одного сайта.
**Решение:** вариант (2). Добавлены поля `src_subdir` (источник rsync — подпапка проекта, а не корень) и `exclude` (доп. excludes поверх базовых `node_modules`/`.git`/`.env`) в схему записи реестра; при `type:"php"` `handleDeploy` пропускает `install_cmd`/`pm2`/`provisionNginxAndCert`, только `rsync` + `chown -R www-data:www-data`. Первый деплой (`firstRun`) для `type:"php"` явно запрещён явной ошибкой — auto-provision nginx+php-fpm для нового PHP-сайта не реализован, заводить такие записи можно только вручную. Итог в registry.json: `krutko77::es-trans-standard` → `test-2.es-trans.ru:3001`/`/opt/es-trans-standard`; `krutko77::es-trans_integration_A1TRACK` → `a1track.es-trans.ru`/`/opt/a1track/www` (`src_subdir:"www"`, `exclude:["env.php","data"]`).
**Почему:** сопоставление по имени папки/процесса ненадёжно (уже дважды подтверждено — сейчас и в D-004) — единственный надёжный сигнал для сетевых сервисов это порт слушателя, а не название. Для PHP — расширение реестра типом дешевле и безопаснее, чем городить второй сервис или пытаться впихнуть чужеродный процесс/порт в node-путь.
**Последствия:** будущие legacy-мэппинги обязаны сверяться через `pm2 jlist`+`ss -ltnp`, а не по имени. Новые `type:"php"`-сайты заводятся только вручную (nginx/php-fpm/сертификат — руками, как раньше); code-path это принудительно проверяет. `es-trans-test`/`test-1` (папка `es-trans-test-OM`) по-прежнему не зарегистрирован — не запрашивалось.
