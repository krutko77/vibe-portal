    API (`https://api.timeweb.cloud/api/v1`, Bearer-токен). Найдено через
    прямое тестирование (не только по докам SDK, которые не совпадают с
    реальным JSON):
    - старый `GET /servers/{id}/statistics?date_from&date_to` отдаёт
      snake_case-поля (`logged_at`, не `loggedAt`, как в SDK-моделях);
      `cpu[]` у этого конкретного сервера **всегда пуст** (проверено за
      неделю), а `ram[]`/`disk[]` приходят нормально;
    - CPU поэтому берётся новым `GET /servers/{id}/statistics/{time_from}/
      {period}/{keys}` (`keys=system.cpu.util`) — там `time_from` это
      **правая** граница окна, а `period` (часы) считается **назад** от
      неё, не вперёд, как ожидалось изначально: для «последних N часов до
      сейчас» нужно подавать `time_from=now`, иначе окно уезжает в
      прошлое;
    - у RAM кроме `used`/`total` есть `used_cached` (МБ) — не
      использовался в первой версии, пригодился в финальном заходе на UI
      (см. ниже).
  - **Несовпадение данных по диску с дашбордом Timeweb** (73%/16.7/6.4/23.2
    ГБ у нас vs 70%/17.3/7.7/25 ГБ у них) — причина: `fs.statfsSync('/')`
    мерит только корневой раздел (`sda1`, 24G), не считая соседние
    EFI/boot-партиции на том же физическом диске (`sda14`/`sda15`/`sda16`).
    Исправлено: `GET /api/vps-disk` теперь берёт `disks[0].size`/
    `disks[0].used` из `GET /servers/{id}` того же Timeweb API — точное
    совпадение с их дашбордом подтверждено числами.
  - Токен `TIMEWEB_API_TOKEN` добавлен пользователем самостоятельно, без
    передачи значения в чат («не хочу передавать его в чат»). Исправлена
