- **2026-09-22 — саппорт-тикет: test-2.es-trans.ru (es-trans_test_standard_MOO)
  не отправлял письма с результатами теста.** Внешний пользователь (клиент
  Kiselev Group, без SSH-доступа к серверу) написал, что после прохождения
  теста показывается «Не удалось отправить письмо руководителю»; сам
  проверил, что ключ UniSender рабочий и код `mailer.js`/`results.js`
  выглядит без ошибок — заподозрил, что `.env` не долетает до pm2-процесса.
  Разобрано на месте (без спроса на риск — только диагностика; сами правки
  подтверждены пользователем через `AskUserQuestion`), найдены **две**
  наложившиеся причины:
  1. **Старая (то, что описано в тикете).** `deploy-service/server.js` при
     каждом деплое `rsync`-ом исключал `.env` даже для `type:"node"` —
     значит `MANAGER_EMAIL`/`UNISENDER_GO_*` физически не попадали в
     `/opt/es-trans-standard/.env`. Код с фиксом (исключать `.env` только
     для `type:"php"`, где прод-секреты живут отдельно от воркспейса) уже
     лежал в рабочем дереве **не закоммиченным** на момент начала этой
     сессии — судя по всему, применён кем-то в предыдущей, недокументированной
     сессии. Сегодня в 05:56 UTC кем-то/чем-то был выполнен реальный
     `POST /deploy` для `es-trans_test_standard_MOO` этим уже исправленным
     кодом — проверено вручную (`node --env-file=... -e "..."` той же
     командой, что использует pm2): все 5 переменных подтверждённо видны в
     `process.env` живого процесса. Эта часть тикета закрыта.
  2. **Новая, регресс от того самого передеплоя.** У rsync стоит `--delete`,
     а папки `data/` физически нет в воркспейсе ученика (`krutko77`) — она в
     `.gitignore` как рантайм-стор. Значит `--delete` при передеплое снёс
     `/opt/es-trans-standard/data/results/` на проде. В `results.js` перед
     `writeFile` результата не было `mkdir`-гварда (в отличие от
     `saveSharedResult`, где для `SHARED_DATA` такая защита уже была) →
     `ENOENT` → 500 «Внутренняя ошибка сервера» **раньше**, чем код доходил
     до отправки письма — то есть реальный сегодняшний симптом был другим,
     чем в тикете, просто маскировался тем же UI-сообщением на клиенте (или
     тикет описывал более раннее состояние, до передеплоя 05:56).
  Исправлено на сервере (все три пункта — с явным подтверждением
  пользователя):
  - `mkdir -p /opt/es-trans-standard/data/results` + `chown 1000:1000`.
  - В `/etc/vibe-deploy/registry.json` (вне git, в `/etc/`) для
    `krutko77::es-trans_test_standard_MOO` добавлено `"exclude": ["data"]`
    по образцу `a1track` — код `deploy-service/server.js` уже применяет
    `e.exclude` и для `type:"node"` (строка 261), правки кода не требовалось.
  - В `results.js` добавлен `if (!existsSync(RESULTS_DIR)) await
    mkdir(RESULTS_DIR, { recursive: true })` перед записью — **в обоих
    местах**: воркспейс ученика
    (`/data/vibe-students/krutko77/es-trans_test_standard_MOO/src/routes/results.js`)
    и прод-копия (`/opt/es-trans-standard/src/routes/results.js`), файлы
    проверены на побайтовую идентичность до и после правки.
  - `pm2 restart es-trans-standard --update-env` — процесс online, сайт
    отвечает 200 локально (`127.0.0.1:3001`) и через nginx.
  Осознанно **не** гонялся полный E2E-тест с реальными `questionIds` —
  это отправило бы настоящее письмо на `MANAGER_EMAIL` реального
  руководителя с тестовыми данными; проверка велась покомпонентно
  (переменные окружения, наличие каталога, статус процесса).
  **Не проверено:** сам факт, что письмо реально уходит конечному адресату
  — это может подтвердить только повторное прохождение теста человеком
  (см. «Следующие шаги»).
  **Важный побочный вывод:** остальные `type:"node"`-записи в
  `registry.json` (`es-trans-orders`, `es-trans-repairs`, `es-trans-results`,
  `krutko77-test-transport-logistics`, `krutko77-es-trans-test-om`) не
