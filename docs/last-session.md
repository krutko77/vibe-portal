## Ключевые решения
- Root/sudo контейнеру НЕ выдан, реструктуризация портала (снести учеников,
  оставить один admin-контейнер с root) тоже отклонена — оба варианта ломали
  бы модель изоляции курса без реальной необходимости. Вместо этого — узкий
  deploy-service, blast radius ограничен собственными `*.es-trans.ru`-сайтами
  агента. Пользователь явно подтвердил этот путь после объяснения
  последствий («хорошо, возвращайся к варианту с узким сервисом»).
- Легаси-сайты в реестр заносятся ТОЛЬКО после сверки по факту (pid/порт
  слушателя), не по совпадению имени папки/процесса/домена — уже дважды
  подтверждено, что совпадение имён вводит в заблуждение (см. D-004/D-005).
- Для PHP-типа сознательно НЕ реализован auto-provision через API (в отличие
  от Node-типа) — риск получить нерабочий nginx/php-fpm vhost при
  единственном текущем случае использования выше, чем польза от автоматизации.

## Подводные камни
- `deploy-service` слушает `172.30.0.1:8191` как root и выполняет rsync с
  `--delete` + произвольный `pm2`/`nginx`/`certbot` — вся валидация входа
  (домен, entry, install_cmd, project) находится в `deploy-service/server.js`,
  трогать эти регэкспы/проверки нужно очень аккуратно, это единственная
  линия защиты от того, что агент испортит чужой/системный сайт.
- Реестр `/etc/vibe-deploy/registry.json` — вне git (в `/etc/`), при переносе
  на другой сервер его придётся переносить/заполнять отдельно, `git`-коммиты
  этой сессии его не содержат.
- `type:"php"` в deploy-service — новый, единственный живой пример
  использования — `a1track`; если появится второй PHP-проект, стоит ещё раз
  проверить, что `src_subdir`/`exclude` достаточно гибки, не расширять
  сверх необходимого без реального повторного случая.
- Ветка `test-1`/`test-2.es-trans.ru` ↔ `es-trans-test`/`es-trans-standard` —
  лёгкая ловушка при будущих ручных правках `registry.json`: имена процессов
  и доменов НЕ соответствуют интуиции, при сомнении — заново сверять через
  `pm2 jlist`+`ss -ltnp`, не полагаться на память/имя папки.
