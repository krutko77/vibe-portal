## Ключевые решения
- **Архитектура метрик — через API Timeweb, не свой сэмплер.** Пользователь
  явно указал на это направление по ходу сессии: хостинг уже копит историю
  CPU/RAM сам, нет смысла дублировать периодическим опросом и своим
  хранилищем — проще и надёжнее забирать нужный диапазон на лету при
  открытии модалки.
- **Диск считается по данным Timeweb (`GET /servers/{id}`), а не
  `statfs(/)` хоста.** Причина — `statfs` показывает размер без служебных
  EFI/boot-партиций, из-за чего цифры расходились с собственным дашбордом
  Timeweb; пользователю нужно видеть то же число, что у хостинга.
- **Токен `TIMEWEB_API_TOKEN` не запрашивался и не показывался в чате** —
  уже лежал в `/data/config/env/vibe-panel.env`, работа шла без доступа к
  его значению.

## Подводные камни
- `Edit`/`Read` могли отвалиться и в этой сессии отвалились на середине
  (таймаут PreToolUse-хука, `Bash` при этом работал исправно). Если это
  повторится — не биться в те же тулы по кругу, сразу переключаться на
  `Bash`+`sed`/`cat` для чтения и `python3`-heredoc (read → assert old in
  content → replace → write) для правок, как было сделано здесь.
- В `vps-metrics.js` два разных endpoint'а Timeweb для CPU и RAM, и у CPU
  `time_from` — ПРАВАЯ граница окна (не левая) — легко перепутать при
  дальнейших правках диапазонов и получить окно, уехавшее в прошлое.
- `downsample()` теперь усредняет generic-набор числовых полей через
  `Object.keys(points[0])` — если в будущем у точки RAM/CPU появится ещё
  одно числовое поле, оно подхватится автоматически; но если появится
  НЕ-числовое поле (строка/объект) в точке — `downsample` на нём сломается
  (делает `reduce` с `+`), это не проверялось.
