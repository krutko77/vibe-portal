## Ключевые решения
- Не гонять живой end-to-end тест с реальной отправкой письма — приоритет
  «не создать шум в реальном бизнес-инбоксе» выше, чем «получить 100%
  подтверждение прямо сейчас». Вместо этого — покомпонентная проверка
  (env-переменные, наличие каталога, статус процесса, HTTP 200) и явная
  пометка в документации, что финальное подтверждение отложено на
  повторный проход теста человеком.
- Все три правки (restore каталога, exclude в registry, mkdir-гвард в коде)
  применены только после явного подтверждения пользователя через
  `AskUserQuestion` — это прод-сайт и код личного проекта админа, не
  курсовая песочница.

## Подводные камни
- **`node --env-file` не отражается в `/proc/<pid>/environ`.** Он не делает
  реальный `setenv()` на уровне ОС, только заполняет `process.env` внутри
  V8/Node — проверка через `/proc/pid/environ` или через `pm2 jlist`
  (`pm2_env.env`, это env самого spawn, а не то, что `--env-file` подгрузил
  изнутри) даст **ложный отрицательный** результат. Чтобы реально проверить
  видимость переменных из `--env-file`, нужно спросить сам процесс (или
  воспроизвести точную команду запуска вручную и напечатать
  `process.env.X` изнутри Node) — оба «быстрых» способа обманчивы.
- **`rsync --delete` + гитигноренная рантайм-папка = тихая потеря данных.**
  Если в проекте есть каталог, который приложение создаёт и пишет в него в
  рантайме (результаты, кэш, сессии), но который отсутствует в исходниках
  ученика (в `.gitignore`, физически нет на диске воркспейса) — каждый
  редеплой через `deploy-service` с `--delete` его стирает. У `a1track`
  (`type:"php"`) это уже было учтено полем `exclude` в `registry.json`;
  у `es-trans-standard` (`type:"node"`) — не было, до этой сессии. При
  добавлении нового node-проекта в deploy-service — сразу проверять,
  есть ли у него такие рантайм-папки, и сразу прописывать `exclude`.
- Ошибка `ENOENT` при записи результата возникает **раньше**, чем код
  доходит до отправки письма (`results.js`: `writeFile` на строке ~72-73,
  логика письма — только на строке 82+) — то есть один и тот же
  пользовательский симптом на экране («Не удалось отправить письмо
  руководителю») может маскировать совершенно разные серверные причины в
  разные моменты времени. Не считать симптом описанием точной причины —
  перепроверять логи `pm2 logs <slug>` заново при каждом повторном
  обращении, даже если тема тикета выглядит знакомой.
- Не делать живой E2E со стороны сервера, если он бы отправил настоящее
  письмо реальному человеку (руководителю/клиенту) с тестовыми данными —
  предпочитать покомпонентную проверку и просить автора тикета подтвердить
  финал самостоятельно.
