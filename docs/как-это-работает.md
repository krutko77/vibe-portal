# Как на одном сервере живёт много приложений — и почему это дёшево и безопасно

Объяснение архитектуры vibe-portal «на пальцах»: как множество приложений
деплоятся на одном хостинге, не мешают друг другу, изолированы, и почему нам
**не нужно арендовать отдельный сервер под каждое приложение** (в отличие от
схемы Bitrix24 vibecode, где деплой каждого приложения = свой хостинг).

Тут три отдельные проблемы, и каждая решается своим приёмом. Они работают вместе.

---

## 1. Много приложений на одном сервере, и они не мешают друг другу

Ключевой приём — **каждый ученик живёт в своём Docker-контейнере**, а не просто
в папке.

```
Один физический сервер (80.87.104.193)
├── контейнер vibe-аня     (своя ФС, свой Node, свои процессы)
├── контейнер vibe-петя    (изолирован от Ани)
├── контейнер vibe-вася
└── ...
```

Что это даёт:

- **Свой «маленький компьютер» каждому.** Внутри контейнера у ученика свой Linux,
  свой Node 22, свой code-server, свой `workspace`. Он не видит ни файлы соседей,
  ни файлы сервера.
- **Лимиты ресурсов** (`panel/lib/students.js`, `STUDENT_MEM_LIMIT_MB` /
  `STUDENT_CPU_LIMIT`): память 3 ГБ, 1.5 CPU на контейнер. Один ученик не может
  «съесть» весь сервер и положить остальных.
- **Сети не пересекаются.** Все контейнеры в одной docker-сети `vibe-net`, но ICC
  (inter-container communication) выключен — Аня физически не может постучаться
  в контейнер Пети.

А приложения, которые ученики **публикуют**, крутятся внутри их же контейнера на
портах 3001+, и наружу эти порты не торчат вообще. Панель (`panel/lib/publish.js`)
проксирует `https://vibe.../<user>/<project>/` → внутренний IP контейнера. То есть
«деплой» — это не отдельный сервер, а просто процесс внутри уже существующего
контейнера ученика.

---

## 2. Почему это безопасно

Несколько слоёв защиты, чтобы ученик (или сбежавший AI-агент внутри его
контейнера) не дотянулся до сервера и чужих данных.

**На уровне контейнера** — ученик намеренно «обрезан»:

- `--cap-drop=ALL` — сняты все Linux capabilities (не может менять сеть,
  монтировать ФС и т.д.)
- `--no-new-privileges` — не может повысить права даже через setuid-бинарники
- `user: student` (uid 1000), без sudo
- workspace монтируется **только его собственный** (`/data/vibe-students/<user>`),
  шаблоны — read-only

**На уровне сети** (`scripts/setup-iptables.sh`, цепочки `VIBE-FILTER` /
`VIBE-INPUT`) — ученик может ходить **только**:

- наружу в интернет (npm, github, docker hub)
- в один-единственный адрес шима `172.30.0.1:8190`

И НЕ может:

- увидеть другие контейнеры
- достучаться до `127.0.0.1` хоста и его сервисов
- хитнуть публичный IP сервера `80.87.104.193` (блок NAT-loopback)
- найти шим по любому другому адресу

Важная деталь: даже если внутри контейнера что-то пойдёт не так, «вырваться»
к серверным сервисам или к соседям сеть просто не даст.

---

## 3. Главное по деньгам — ключ Bitrix24 vibecode, без «1 приложение = 1 сервер»

AI-доступ (ключ) мы берём у **Bitrix24 vibecode** (https://vibecode.bitrix24.tech/).
И вот в чём принципиальная разница в схемах деплоя:

```
Схема Bitrix24:  приложение №1  →  свой арендованный сервер
                 приложение №2  →  свой арендованный сервер
                 приложение №3  →  свой арендованный сервер
                 ...каждое приложение тянет за собой отдельный хостинг

Наша схема:      приложение №1 ┐
                 приложение №2 ├──► ОДИН наш сервер
                 приложение №3 ┘    (контейнеры + прокси)
                 ...ничего арендовать не надо
```

У Bitrix24, чтобы задеплоить приложение, под каждое нужен отдельный сервер.
У нас все приложения живут на **одном** сервере — арендовать под каждое не нужно.

Технически это вытягивает **anthropic-shim** (`shim/server.js`) — реверс-прокси
на хосте на порту 8190, который держит ключ централизованно:

```
claude-cli ученика  ──►  шим (:8190)  ──►  upstream API
   (фейковый токен)       подставляет
                          настоящий ключ
```

Как это работает по шагам:

1. У ученика в контейнере прописан `ANTHROPIC_BASE_URL=http://172.30.0.1:8190`
   и **фейковый** токен `sk-vibe-shim-placeholder`. Реального ключа у ученика
   нет вообще — даже если он залезет в env, там пусто.
2. Запрос летит не наружу напрямую, а в шим.
3. Шим **срезает** фейковый `Authorization` и подставляет **настоящий**
   OAuth-токен из credentials-файла на хосте (`creds.accessToken`,
   `shim/server.js`).
4. Форвардит в upstream API.
5. Сам **авторефрешит** токен за минуту до истечения — ученикам/приложениям
   ничего обновлять не надо.

Что это даёт по деньгам: ключ живёт **в одном месте** (шим) и обслуживает все
приложения на сервере. Вместо «каждое приложение → свой сервер со своим ключом»
— один сервер, шим раздаёт доступ всем. Сменить или добавить аккаунт = подменить
credentials-файл и `systemctl restart anthropic-shim`, контейнеры не трогаем.

Бонусом шим ещё и **пишет аудит** всех диалогов (`shim/transcript.js`) —
определяет ученика по IP контейнера (подменить IP нельзя, т.к. `CAP_DROP=ALL`),
пишет JSONL, а admin смотрит на `/logs.html`.

## 4. Как у одного ученика много приложений, и они не мешают друг другу

Один ученик = один контейнер, но внутри него он делает **много проектов**, и
каждый можно опубликовать как отдельное работающее приложение. Они не толкаются,
потому что у каждого приложения своё всё (`panel/lib/publish.js`):

| Что у каждого приложения своё | Где это |
|---|---|
| Отдельная папка проекта | `workspace/<project>/` |
| **Свой порт** (3001, 3002, …) | `allocatePort()` — берёт минимальный свободный, сканируя порты всех проектов ученика |
| Свой конфиг публикации | `.portal-meta.json` → `publish:{enabled, visibility, autosleep, port, cmd}` |
| Свой процесс | `nohup` в `docker exec -d`, pid → `.publish/app.pid` |
| Свой лог | `.publish/app.log` |

Как это собирается воедино:

- **Раздача портов.** Когда ученик публикует проект, `allocatePort()` проходит по
  всем его проектам, смотрит уже занятые порты в их `.portal-meta.json` и выдаёт
  первый свободный из диапазона **3001–3099**. Поэтому приложение А и приложение Б
  никогда не сядут на один порт — коллизии нет by design.
- **Запуск.** `detectCmd()` сам определяет стек проекта и команду:
  Node → `env PORT=<порт> node <entry>`, PHP → `php -S 0.0.0.0:<порт>`,
  статика → тоже `php -S`. Перед стартом `deployApp()` сначала глушит старый
  процесс на этом порту (`stopApp`), потом поднимает новый.
- **Маршрутизация.** Панель проксирует `/<user>/<project>/*` →
  `http://<containerIP>:<port>/` — то есть по **имени проекта** в URL понимает,
  на какой внутренний порт слать. Снаружи порты 3001+ не торчат вообще.
- **Self-heal.** Заход на URL приложения будит контейнер и переподнимает процесс,
  если он умер (`ensureRunning` → проверяет «живо ли на порту», если нет —
  передеплоивает).

Что важно понимать про границы изоляции:

- **Между учениками** — жёсткая изоляция: разные контейнеры, разные сети, разные
  workspace (разделы 1–2).
- **Внутри одного ученика** — приложения логически разведены (порт + процесс +
  папка + лог), но делят **общие ресурсы контейнера** (RAM 3 ГБ, 1.5 CPU). То
  есть они не конфликтуют по портам и файлам, но если одно приложение прожорливое
  — оно ест общий лимит контейнера этого ученика. Это осознанный компромисс:
  внутри своего контейнера ученик сам себе хозяин.

## Если совсем коротко

| Проблема | Дорогой путь (в т.ч. Bitrix24) | Как сделано здесь |
|---|---|---|
| Деплой приложений | каждое приложение → свой арендованный сервер | все приложения на 1 нашем сервере |
| Много учеников | N серверов | N контейнеров на 1 сервере |
| Не мешают друг другу | физическая изоляция | Docker + лимиты + iptables |
| Безопасность | отдельные VM | cap-drop + сеть-белый-список + bind свой workspace |
| Много приложений у ученика | по серверу/хостингу на каждое | свой порт + процесс + папка в одном контейнере |
| AI-ключ (Bitrix24 vibecode) | ключ привязан к серверу приложения | ключ в шиме, раздаётся всем приложениям |

Суть всей экономии — **переиспользование одного сервера через изоляцию**:
один наш сервер вместо «по серверу на каждое приложение», а ключ Bitrix24 vibecode
живёт в шиме и обслуживает все приложения сразу.
